# LLM Coding Agent Anti-Patterns

**Status:** current · **Owner:** CORSIA maintainers

Cumulative catalog. Add new behavior shapes at the end, but amend an existing
entry when it names retired authority or would teach a now-false rule. Each
entry has a short general headline, one explanatory paragraph, and one compact
historical example. The goal is recognition in unfamiliar code, not preserving
obsolete process as immutable text.

---

### #1 — Memorializing settled changes

Adding artifacts (code, tests, comments, flags, logs) whose only job is to *refer to* a change the agent just made — assert a deletion happened, comment that code used to be here, log when a removed path didn't fire, default-arg the absence of a value, write a migration that re-cleans already-clean state, leave a deprecation warning for already-dead code. The change is its own record (git history, working code, real-flow tests); memorial artifacts add no signal and compound forever. Shape: any new artifact whose only job is to refer to a *different* artifact's absence, deletion, or version.

*Example (CORSIA Phase 7 mlxd rip, 2026-05-08): tests asserting deleted symbols don't exist, deleted dispatch keys raise on lookup, removed branches don't route. Stripped in the same cleanup pass.*

### #2 — Reactive guards that reconcile user-controlled state

Adding a background loop, health-sweep hook, sync routine, or "ensure" function that watches a user-controlled value (model loaded, branch checked out, feature flag on, file present) and automatically writes the "intended" value back when it drifts. The guard treats the symptom as the problem and buries the actual cause — whatever wrote the wrong value goes uninvestigated because the watchdog rewrites it before anyone notices. It also smuggles a parasitic second meaning into the state ("watchdog will reset this") on top of the original ("user/system set this"), and the user's deliberate deviations always lose without being told why. The right move is to instrument the path that broke the invariant — logs, metrics, surfaced warnings — never auto-correct. Shape: a watchdog/sweep/"ensure" loop that silently rewrites a value whose authority is a **deliberate user/operator choice** (a pinned model, a checked-out branch, a toggled flag) back to a system-"intended" value — overriding *intent* and burying whatever set it wrong. **NOT this:** reconciling *system-owned* desired-state — controllers, idempotent provisioning (ensure-table-exists), reconnect/retry, token/lease renewal — where there is no user authority being overridden; those are correct by design. The pattern is specifically the silent override of a human's deliberate choice.

*Example (CORSIA oMLX 27B unload, 2026-05-10): proposed a CORSIA health-sweep guard that auto-loads any pinned-but-unloaded model. Rejected — pin means one thing (oMLX won't LRU-evict); a CORSIA auto-reload would steamroll deliberate user unloads. Real fix was raising oMLX log level to find the actual cause.*

### #3 — Creating new artifacts without searching for existing ones

Writing a new file, spec, doc, helper, or catalog to satisfy a request without first searching the workspace for an equivalent — especially when the user has just *said* one exists. Produces parallel sources of truth that immediately fight: docs that disagree, settings duplicated in two places, two catalogs to keep in sync. The cost isn't the moment of duplication; it's the slow drift afterward that nobody can fully undo. Always grep first by exact name, semantic name, and one or two synonyms before writing a fresh top-level artifact. If the user implies it should exist, treat that as confirmation, not a "well, I couldn't find it" — search harder. Shape: a new file whose name or purpose could plausibly already exist in the workspace, created without exhaustive grep-checking first.

*Example (this catalog, 2026-05-10): asked to track an anti-pattern in the workspace, created a new `ANTI-PATTERNS.md` at workspace root despite `llm-anti-patterns.md` already existing. The project owner had to point it out. Duplicate file deleted; the entry that triggered the creation (#2 above) was appended here instead.*

### #4 — Hardcoded model names as runtime defaults

Embedding a string-literal model name (`"hosted_vllm/Qwen3.5-35B-A3B"`, `"anthropic/claude-haiku-4-5"`, `"openai/gpt-5-mini"`) as the fallback in `defaults.get("model", <literal>)`, as a module-level constant holding a model id, or as a sentinel `LOCAL_MODEL = ...` "in case nothing else sets it." Looks reasonable at the moment of writing — the model was current, the catalog had it. Six months later the catalog has moved on (3.5 → 3.6, sonnet 4-5 → 4-6) but the literal is still there, silently routing every uncaught code path to a model that no longer exists. CI breaks with "model not found in catalog" errors that look like infra problems but are actually code-level rot. The right shape: take the model from the operation's own input or from the thread's model target, and **raise loudly** when it is missing — never substitute a fallback, literal or runtime. There is no global default model: a turn carries its own target and every system or background operation takes an explicit model input. Catalog/pricing/registry data files are different (their job IS to know specific model IDs); a runtime fallback is not. Shape: a model-name string literal in non-data, non-test code, especially in a default value, fallback, or "ensure something" sentinel.

*Example (CORSIA Sprint 3 closeout, 2026-05-15): `LOCAL_MODEL = "hosted_vllm/Qwen3.5-35B-A3B"` survived the oMLX migration as dead code in `infra/config.py` AND as the fallback in `core/agent.py:get_agent()`'s `defaults.get("model", "hosted_vllm/Qwen3.5-35B-A3B")`. CI's e2e job (which has no GPU and no oMLX daemon) hit the missing-default error long after the actual model went away. Fix: rip the literal, give every operation its own explicit model input, and raise when it is absent. New `tools/antipatterns/rules/hardcoded_model_name.py` rule (severity=error) catches future occurrences at commit time.*

*Sub-example (CORSIA, 2026-05-22): same shape, different literal — `backend/llm/capabilities.py:47` had `row.get("context_window") or 128000` and `backend/llm/catalog.py:282` had `mc.get("max_input_tokens") or 128000`. oMLX network discovery was reading the wrong endpoint (`/api/status:context_length`, doesn't exist) → catalog rows persisted NULL → the `or 128000` fallbacks silently halved Qwen 3.6's real 256K window. Every compaction trigger + cost-cap calc on the local stack ran with the wrong number for months. Fix: build a centralized resolver in `backend/llm/context_window.py` that raises `ModelContextWindowUnknown` on a broken catalog rather than substituting; fix discovery to read `/v1/models/status:max_context_window`; rip every `or 128000` and the schema `DEFAULT 128000`. Same anti-pattern as the original entry — model-related runtime fallback literal that masks a discovery / config bug as a normal-looking value.*

*Sub-example (CORSIA, 2026-06-11 — the recurrence is an ENFORCEMENT gap, not a new literal): the literals came back a 3rd–4th time (`router.py` default param, `prompts/fact_extraction.py`, `resource_manager.py`, every `eval/*` judge/proposer default, the schema `judge_model ... DEFAULT 'anthropic/...'`, `scripts/corsia`'s `DEV_DEFAULT_MODEL`, `scripts/e2e-local`). They drained a separate API account across several models through an unscrubbed reviewer environment and inherited subagent defaults, until it hit its balance limit. **Root cause of the recurrence:** the guard already existed — anti-pattern #4 + the `hardcoded_model_name` rule (severity=error) — but it was wired ONLY into `.pre-commit-config.yaml`, **never into `.github/workflows/`**. Any agent/commit that skipped pre-commit (`--no-verify`, a different harness, a squash) landed the literals unchecked. The lesson: **a lint rule that isn't a blocking CI gate is advisory in practice** — it catches the careful, not the careless, and the careless are exactly who reintroduce the literal. Two compounding holes: (1) pre-commit-only, so no CI backstop; (2) the rule's exclusions whitelisted the defaults — `infra/schema.py` was in `data_file_globs` ("a DB DEFAULT is data"), but a model the user didn't choose IS the anti-pattern. Fix (the enforcement, not another manual rip): rip the literals + require every operation to pass its own model input and fail loud when it is missing; **promote the rule to a blocking job in `.github/workflows/antipatterns.yml`** (whole-repo `--all --severity error`, no `|| true`, runs on PRs to both `dev` and `main`); drop the `schema.py`/`config.py` exclusions (keep catalog/pricing/capabilities); teach the rule to catch model literals embedded in SQL `DEFAULT '<provider>/<model>'` clauses (the anchored whole-string pattern couldn't see DDL-embedded ids). When a rule recurs, the durable fix is the gate, not the cleanup.*

### #5 — Multi-branch edits at a shared file anchor

Opening N independent PRs that each insert at the same line/anchor in a shared file (registry, config, central index, large constants block, lookup table) — they merge in isolation but cascade-conflict against each other. The first PR merges clean; the next N-1 must rebase against the new state and resolve conflicts at the same anchor. Each rebase generates noise — force-push notifications, CI re-fires, GH conflict-state flips, ready-vs-draft churn — and the user ends up playing merge-conductor instead of approving content. The agent then layers cron-rebase loops, janitor agents, and "cumulative content" tricks on top, compounding the mess. The right shape, named upfront: when N changes share an anchor in a single file, **bundle them into ONE PR per batch** (or stack them as dependent branches with shared base) so there's exactly one merge for that anchor. Per-item PRs are right only when diffs are fully disjoint across all branches; collision on a shared file is the disqualifier. Count `branches × shared-anchor-file` before pushing — if > 1 anywhere, bundle.

*Historical retired-spec example (CORSIA Sprint 5 priority-1 backfill, 2026-05-16): eight PRs edited the same registry anchor and cascade-conflicted after the first merge. Two manual rebase cycles, a cron-rebase loop, and a cumulative-content restructure produced more notification noise than progress. Bundling the remaining six changes produced one review, one merge, and zero further conflicts. The old spec/registry process is retired; the enduring lesson is to bundle changes that share one load-bearing anchor.*

### #6 — Annotate the drift, don't amend the current authority

When a current PRD, acceptance contract, test matrix, or operating standard drifts from landed behavior, the easy move is to add a side note saying "stale" instead of reconciling the authoritative requirement or the implementation. The contradiction then remains live: agents and gates can enforce the old rule while commentary describes the new one. Fix the current authority and its executable checks together, or fix the code when the authority is still correct. Archived ADRs and subsystem specs are historical evidence only: never update, reactivate, or treat them as reviewer authority. The retired `spec-gate` and `pr-format-check` are not consumers. Shape: drift discovered, mismatch memorialized outside the current authoritative requirement, original contradiction left in force.

*Historical example (CORSIA Sprint 5 audit, 2026-05-19): when subsystem specs were still live authority, §0.0 retained obsolete environment and tool-count rules while later sections merely labeled them stale, so gates and reviewers enforced the wrong contract. Those specs and gates are now retired. The durable lesson is to reconcile today's current PRD/AC/standard and executable checks rather than annotate a contradiction or revive the archived artifact.*

### #7 — Hardcoding the user's name into code, docs, or identifiers

Putting a specific person's name into any artifact that lives in the repo — function names, tool names, event types, variable names, class names, comments, doc prose, spec body, README, ADR. The artifact becomes wrong for any second user (including a forked / open-sourced version), commits the codebase to a single-tenant assumption it didn't have to make, and bakes in a maintenance tax: every rename later touches every artifact + every fork. The right shape is to name the *role* — `user`, `operator`, `principal`, `owner` — and reserve the proper noun for human-only contexts (chat transcripts, USER.md, the actual person's identity file). Treat the same way you'd treat a hardcoded environment-specific path or model name: it's data, not code. Shape: any non-data file in the repo that names a specific real human in an identifier OR in repeated prose where the role would carry the meaning equally well. Carry: every new artifact gets a name-grep before commit.

**Not in scope: test seed and fixture data.** A synthetic value a test writes or seeds — `user_id='alice'` in an `INSERT`, a fixture credential, sample payload content — is data, not an identifier or prose, and is exempt even when the whole suite shares it. Do not raise a finding that asks an author to diverge from the fixture their test already inherits; a value the repo seeds in dozens of files is a shared fixture, and changing it in one test is churn with no second-user benefit. Still in scope inside test files: the *identifier* cases — a test helper, class, or event named for a person — and repeated prose in comments or docstrings.

*Historical retired-spec example (2026-05-20): a design draft named a tool `ask_alice`, an event `subagent.asked_alice`, an event family `alice.{answered_question, redirected_subagent}`, and repeated the person's name where "the user" carried the same meaning. The old subsystem/ADR artifacts are retired; the durable correction was role-based names (`ask_user`, `subagent.asked_user`, `user.{answered_question, ...}`).*

### #8 — Memorial KPIs in spec clothing

Adding a §0.5 KPI whose existence is justified by a specific bug filed yesterday — "regression sentinel," "watches for #N," counts the exact shape of a fix that just landed. The KPI looks like a health metric but it's really a regression test in disguise: binary (0 vs not-0, "did the bug come back?"), tied to one specific failure mode, and useless if the bug never existed in the first place. KPIs should measure ongoing properties of normal operation — continuous ranges (latency p95, FPS, count-per-day), or invariants that should always hold across many different code paths. Regression tests catch specific bugs; KPIs measure subsystem health. Mixing the two pollutes §0.5 with metrics that don't help an operator answer "is this subsystem behaving normally right now?" — and they grow forever as more bugs land. Rule of thumb: if you can't describe a KPI without naming a specific issue number, it's not a KPI — it's a regression test that wandered into the wrong section.

*Example (CORSIA Sprint 22 parallel-cleanup, 2026-05-22): the cleanup-sprint spec fixups added `omlx_alias_canonical_dupe_count` ("regression sentinel for bug A"), `typewriter_cross_session_leak_count` ("bug B regression sentinel"), and `turn_complete_delta_drop_rate` ("bug C regression sentinel") to §0.5 tables. Each was justified solely by a bug just fixed. The actual regression coverage was already in place — 9 pytest cases in `test_catalog_omlx_dedup.py` for bug A, 15 vitest cases in `streaming-session-bound.test.ts` for bugs B and C. The project owner flagged the pattern; KPIs reverted; spec template + this entry added so future authors hit the rubric instead.*

### #9 — Silent success on unparseable model output

When a pipeline shells out to a model (or any flaky external producer) and feeds whatever comes back straight into a lenient parser, the error channel and the data channel collapse into one string. The failure mode: the call fails (billing, outage, rate limit), the error text lands where output was expected, the parser shrugs ("not valid JSON → return empty default"), and the empty default reads downstream as a *clean result* — the pipeline doesn't just hide the failure, it forges a positive verdict. This is the worst species of silent fallback because it inverts the signal: infrastructure-down presents as quality-passed. The right shape: validate the transport envelope (exit code, `is_error`, subtype) BEFORE touching the payload; classify errors on the error channels only (never sniff the success payload for error keywords); make the parser raise on garbage — an empty/default value may only ever be produced from a successfully parsed input (a clean review is the literal `[]`, not unparseable text); and a gate that can't produce a verdict FAILS visibly (core constraint #6). Shape: any `except`/fallback between an external producer and a quality gate that converts an unreadable response into the gate's passing value.

*Example (CORSIA reviewer incident, 2026-06-09/10): API credit exhaustion made `claude -p` print "Credit balance is too low"; `invoke_cc_subagent` raised only when rc≠0 AND stdout empty, so the error string flowed into `parse_findings`, which returned `[]` on unparseable input; the workflow posted "0 block, 0 flag, 0 nit" SUCCESS on seven PRs for ~15 hours — fake green at the exact gate auto-merge trusts. Fix: strict envelope validation (raise on `is_error`/non-success subtype), `ReviewerOutputError` from the parser, model-unavailable → the `qa/llm-reviewer` check FAILS.*

### #10 — "It's just a flake" as a merge excuse

Treating a nondeterministic test failure — passes locally / fails in CI, passes alone / fails in a suite, passes on re-run — as a dismissible "flake" and merging or ignoring the red (often via `--admin`) instead of root-causing it. "Flake" is a smell word meaning "root cause not found yet," not "spurious failure, safe to dismiss." Nondeterminism is ALWAYS a real defect: an isolation leak, a race, unreset shared/global state, a timing/order dependency, or a cross-environment version skew. Why it's bad: the moment "probably just the flake" is an acceptable reason to merge over a red, the gate is worthless — every red becomes ambiguous and a genuine regression hides behind the same excuse ("probably the flake again"); the flaky test rots in place across many PRs, each author `--admin`-ing past it, until the real bug it was masking ships. Determinism (same input → same result, every time) is a hard requirement, not an aspiration; a test that can't meet it is itself broken. Right shape: any nondeterministic / order-dependent / CI-only-failing test → root-cause + fix immediately, OR explicitly quarantine with a tracked bug issue + a deadline, loud and visible (skip-with-reason + link) — never silent tolerance, never `--admin`-past-as-routine. Treat every red as REAL until root-caused; surface latent signals (un-awaited-coroutine warnings, "event loop closed" on teardown) as failures (`-W error`); audit suites for the leak classes (async-mock, shared-state, order-dependence, loop-scope); and pin dependencies so local==CI leaves no version-skew hiding place.

*Example (CORSIA dev-to-main promotion, 2026-06-14): `test_mock_router_isolation` failed CI-only across ~6 PRs, each merged `--admin` "over the flake." Two false root causes were chased — an un-awaited AsyncMock in `test_event_routing` (a real latent defect, but not this failure's cause) and a claimed Starlette `_IncludedRouter` type that doesn't exist — before the real one: `app.routes` returning route-wrapper objects under FastAPI 0.137 (CI) vs 0.135 (local), an unpinned `fastapi>=0.115.0` version skew. Fixed at root with a version-resilient route walk + `asyncio_default_fixture_loop_scope=function`, plus a dep-pin (local==CI) and a suite-flakiness audit. The interim self-merge policy's "--admin OK when the sole red is the isolated flake" allowance was superseded: no dismissible flake — root-cause, or loud-quarantine-with-deadline.*

### #11 — Silent cross-function failure (a caller leans on a swallowed write)

A function that **silently swallows its own failure** — catches its error, logs at most a warning, and returns `None`/best-effort — on a path a **caller depends on for a correctness- or durability-critical outcome**. The caller leans on a write that may not have happened; neither the callee nor a diff-scoped reviewer can see the dependency, so nothing surfaces until something downstream is quietly wrong. This is the **cross-function** form of the loud-failure rule (cf. #9, the producer→gate form): the failure crosses a *function* boundary instead of a process boundary. Fix: **surface the failure** — return a status the caller checks, or raise — so the dependency is visible and a caller cannot silently lean on a swallow. **NOT this:** a function legitimately depending on a caller's lock, a documented precondition, or an `_unlocked_` helper called under the caller's lock — that is ordinary layered/contract design, and pulling the guard "local" can be *actively wrong* (e.g. a double-lock). The only ask there is to **state the precondition in one line and `assert` it** so it's locally checkable. Shape: a callee that hides a failure its caller's correctness depends on — or a non-obvious precondition left unstated and unasserted.

*Example (CORSIA cc_runtime, 2026-06-22): `register_cc_session()` caught its own DB errors, logged a warning, and returned `None`; the CC cold-start path silently depended on that write to persist the thread→CC-session resume mapping — a swallowed failure would have lost the binding with nothing surfaced. Fix: surface the registration result so the caller can react. (Two sibling observations from the same code were NOT durable shapes: a lock held on two `feed()` branches but omitted on a third is just a concurrency bug caught on its own merits; and "make the invariant local" was the wrong generalization — `resume_child` correctly relies on `feed`'s lock, and re-locking inside it would deadlock.)*

### #12 — Unapproved migration bridge / fallback (preserve-the-old-path instead of replace)

When a change would break old data or old behavior, adding a **fallback / dual code path / "mirror" / compat shim / legacy-preserving branch** so both the old and new way keep working — *instead of migrating to the single new path*. It feels safe (nothing breaks) but it is permanent dual-path debt: two code paths for one concept, more surface to reason about, the exact complexity the system keeps fighting. A "fallback" with no committed removal step **is** the second path forever. The trap is especially seductive when a **reviewer flags "this breaks legacy X"** — that is NOT license to restore a fallback; it's a signal to *migrate X*. **What to do instead:** replace, don't preserve — migrate the old data/callers to the one new path (backfill / transform), then there is nothing to fall back to. If migration is genuinely out of scope, **STOP and get explicit approval** before adding any bridge; a temporary bridge requires both approval and a committed removal step. Treat any urge to write `fallback`/`mirror`/`compat`/`legacy path`/`for backwards compat` as a hard stop-and-check. Shape: "old way still works too" added without an approved, time-boxed migration plan.

*Example (CORSIA artifacts A2.5, 2026-06-23): a reviewer correctly flagged that the new normalized owner-resolution dropped routing for un-mirrored (pre-A1) artifacts; the "fix" **restored the legacy `resolve()` fallback** in `owning_thread_for_identity` — re-introducing a permanent dual path nobody approved. The right fix was a one-time backfill mirroring every legacy `artifacts` row into the normalized identity system, then **deleting** the fallback → one path. (Recurring offense — ~5×; now a binding `AGENTS.md` rule: "Replace, don't preserve — never add a migration bridge/fallback without explicit approval.")*

### #13 — New surface layered over the old equivalent surface

Shipping a new product surface for a concept while leaving the old surface for the same concept alive in the same user journey. The new component may be correct in isolation, but the composed UI now has two labels, two severity systems, or two "sources of truth" for one user job. This is especially bad for attention/triage surfaces: the old pane often carries raw activity, stale history, repair debt, or implementation artifacts, and once it sits under the new "real" surface the user sees a contradiction rather than hierarchy. The right shape is replace-or-demote: before adding a new surface, inspect adjacent panes in the same viewport and state what old concept is removed, renamed, collapsed, or made passive. Component tests and design demos are not enough; the gate must review the composed live surface with realistic data. Shape: a PR adds `New X` but leaves `Old X` visible nearby, so the user sees two competing Xs.

*Example (CORSIA coordination MVP conductor pane, 2026-06-27): two PRs shipped `Requires disposition` as the new parent-disposition/user-attention surface, but left the old `ArtifactPane` amber `Needs you` lane directly beneath it. On dev, `Requires disposition` correctly said nothing needed action, while `Artifacts > Needs you` showed 11 stale/internal rows: failed test subagents from 9-11 days earlier, missing scratch artifacts, raw path-derived repair rows, and a pending `describing...` code artifact. Standards review checked the new component in isolation and missed the composed first viewport. Fix: make the artifact pane stop acting as a raw attention surface — settle stale workers, collapse repair/history, hide raw internals, and enforce one attention concept per first viewport.*

### #14 — Mechanical presence check passed off as UX review

Reviewing a user-facing change by confirming that the component mounts, the route appears, the button is wired, tests pass, and no console errors fire — then calling it "UX reviewed." That is implementation verification, not UX judgment. A real UX review starts from the user's job and asks whether the surface lowers cognitive burden without creating worse tradeoffs: what information is over-prominent, duplicated, stale, confusing, or missing; what should be removed, collapsed, renamed, or delayed; whether the first viewport communicates the right priority; and whether the user now has fewer decisions to make. The right shape is a composed-surface review with realistic data and a written verdict on cognitive burden and negative consequences. Shape: a review report that says "it renders / it is scoped / it has labels" but never says whether the resulting experience is good, quiet, understandable, or worth putting in front of a user.

*Example (CORSIA conductor pane, 2026-06-27): two PRs passed several mechanical gates — the `Requires disposition` section mounted, was scoped to the conductor, had no duplicate header, had tests, and had an isolated browser smoke. Nobody reviewed the actual dev first viewport from the project owner's perspective with real artifact data. The result showed an empty important queue followed by a noisy amber `Needs you` lane full of stale/internal debris, increasing cognitive burden instead of reducing it. Fix: require a live-dev evidence packet plus a user-perspective UX verdict before any project-owner-facing dogfood request.*

### #15 — Designing the new component instead of the loaded existing surface

Creating a design brief or UX pass around the new component alone, while the real user experience is the existing shell with old panes, legacy lanes, noisy data, empty states, repair states, history, and mobile constraints around it. This misses the failures users actually feel: duplicate concepts, bad priority, stale rows, confusing neighboring labels, and cognitive load that only appears when the surface is fully loaded. The right shape is a fully loaded existing-surface brief before build: current-surface audit, replacement map, in-context prototype/fixture, empty/normal/full/error/stale/mobile states, and a test hook that can replay the loaded state after implementation. Shape: "design approved" based on a clean isolated mock, followed by a live surface where the component is technically correct but the page/pane is worse.

*Example (CORSIA conductor pane, 2026-06-27): the design review for `Requires disposition` reasoned about the new pane and then the mount, but not a fully loaded conductor right pane containing the existing `Artifacts` lanes. A pre-build fully loaded fixture would have shown that the old `Needs you` lane dominated the same viewport with stale failed subagents and repair debris, invalidating the design before code was written. Fix: require the fully loaded existing-surface brief and test path for user-facing surface changes.*

### #16 — Review-feedback whack-a-mole

Treating each reviewer comment as a new patch instruction, pushing again, then repeating when the fix exposes another defect. This optimizes for closing comments instead of restoring a coherent design; adjacent reviewer requests also get mistaken for authorization. Classify first: infrastructure/same-head reruns/nits/settled duplicates do not count. A new substantive finding on each of two distinct revised heads is an architecture hold: stop edits, commits, pushes, and review reruns; name the state owner, write the transition/failure matrix, root-cause why preflight missed both, and produce a test-first plan. A third candidate requires explicit user authorization. Reviewer findings can block or request re-scope; they never expand scope themselves.

*Example (CORSIA repo-isolation PRs, 2026-07-09): successive broad fixes grew a small worker/serving separation into a policy framework and dozens of adjacent enforcement changes. The repair was to close both heads, restore the narrow scope fence, rebuild from current `dev`, and stop treating newly discovered adjacent risks as implementation authority.*
