# Assistant Google setup

You own this setup. Run it in your own thread, never the conductor's, so the Google credentials land in your own Google Workspace home, which your shell and your scheduled email check both read. Show the whole plan first. The user approves one install if the tools are missing, signs in to Google and clicks Allow; perform every other step. Do not read credentials, print them, or call an external service until the user reaches the relevant step.

1. Run `gws --version` and `agent-browser --version`. If either is missing, install both yourself: call `request_host_access` for exactly `brew install googleworkspace-cli && npm install -g agent-browser@0.31 && agent-browser install`, stating that the user chose the assistant and that nothing else is installed or changed. Once it is approved, run that command with host scope and tell the user the browser download takes a few minutes. If access is refused or unavailable, give the user that one Terminal command instead and wait until they say it finished. Check both again before continuing. Never run Homebrew from the protected agent shell, and never npm either. The `@0.31` pin is the build CORSIA's browser tools accept; an unpinned install can fetch a newer build they refuse.
2. When `agent-browser` is available, use its visible, headed session (`browser_open` with `show_window: true`) for each non-human Google Cloud Console action: create/configure a Cloud project, enable Gmail/Calendar/Drive/Docs APIs, configure the OAuth consent screen, create a Desktop OAuth client, and capture its download. Do not use a hidden browser. Follow `.corsia/skills/conductor-bootstrap/references/browser-person-steps.md` for every step that is the person's. Open the Cloud Console first; when Google shows a sign-in, password, 2-Step or passkey page, the browser is the user's: tell the user with `post_update` to sign in in that open window, then watch per that file's B, reading only the URL and title; never type, fill or read a password yourself. Once they are signed in, take over. If Google then shows a terms-of-service or consent page, ask the user to accept it in the open window (`post_update`, then watch per that file's A with `browser_wait` and reading only the URL and title), and continue the moment it clears; a captcha page with no password field is watched the same way, and you never solve or bypass it. If `agent-browser` is unavailable, show every numbered manual Cloud Console step in `.corsia/skills/assistant-onboarding/references/google-cloud-setup.md`; do not promise that Download is the only user action.
3. Source `.corsia/skills/assistant-onboarding/assets/gws-env.sh --client-json "<downloaded-client-json-path>"` without reading, printing, or pasting the file. The helper moves it into your own Google Workspace home outside the workspace (named by `CORSIA_GWS_HOME`, readable and writable by this thread's shell only; the helper fails if the variable is missing) with mode 600 and exports client values only inside the current shell. If browser automation reaches the client page but cannot capture the download, the user's one extra action is clicking Download. Do not claim browser setup was proven without a real test.
4. Source the same helper and run `gws auth login --scopes https://www.googleapis.com/auth/gmail.modify,https://www.googleapis.com/auth/gmail.send,https://www.googleapis.com/auth/calendar,https://www.googleapis.com/auth/drive,https://www.googleapis.com/auth/documents`. The user alone chooses an account and clicks Allow.
5. Validate Gmail, Calendar, Drive, and Docs independently with one read each, following the attached `assistant-google-workspace` skill. Name the failed service and one fix, then re-check only that service.
6. Post a linked, read-only first result with `post_update`. Do not send or write while producing it. Then follow your `assistant-email-check` skill for the schedule.
