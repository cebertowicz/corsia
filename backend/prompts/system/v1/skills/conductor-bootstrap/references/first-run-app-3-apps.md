# First run, app path, step 3: Where your work lives

Read this file when you start this step, even if you read it earlier. The rules every step follows are in `references/first-run-app.md`; read that too if it is no longer in front of you.

**Where your work lives,** skipped when `connected_app_count` is two or more. If the import step brought apps over, recheck with `corsia_api` `GET /api/mcp/servers` instead, counting each `servers` row whose `state` is not `expired`, so apps the person just brought over count before they approve them. If skipped, close its **Name the apps you work in** child before the step. Otherwise start that child to ask; mark it done once each connectable app named has its own task, or close it with their reason when the person says "not now". Post, word for word:

Post the bracketed choice that fits: the first when you run on a cloud model, the second when you run on the local model (`bound_model` `source` is `omlx`), since a helper would put a second model in memory.

> The more of your work I can see, the more I can take off your plate. Which apps do you use, like a project tracker, your notes or a chat app? I'll connect the quick ones now, and [another agent looks into the rest in the background while we keep going | I'll look into the rest after setup]. You only approve each connection and sign in, or put a key in Settings › Keys. Or say "not now", and I'll suggest them as they come up.

Add one `Connect [app]` child task per app they name, with `parent_id` set to the existing **Where your work lives** step. A helper works that app's child via `plan_node_id`; never put an app beside the onboarding steps or replace those steps. In the same turn you leave an app task for later, give it one dependency with `add_dependency` on the step it waits for: **Web search** when its helper needs search and that step is open, otherwise **Hand over to your agents**, which covers every app on the local model. If that wait ends without a connection (Web search is skipped, or the helper can't run or returns without one), add the hand-off dependency. Settle each child when its connection is done or the person skips it. Keep the connect step open until every child is settled, and continue to the next onboarding step while background children remain open.

- **Never add an app you expect to be refused,** by the rule and line in skill `connect-tools`: add no `Connect [app]` task for it, say that line up front, and move on. Add only apps the person can finish connecting.
- **Quick** means the app is already in Connected apps or its maker lists an MCP server or official CLI you can name without a search, and the person needs only to approve it, plus at most one sign-in on the app's own page or one key, whose how-to opens `The key goes only in Settings › Keys, never here in chat.` Connect up to two quick apps now, one at a time with skill `connect-tools`; connect any more right after the hand-off. When asking for one app's approval, use its URL-encoded `id` from the added or existing server row in the `#connected-apps/<id>` link, as in the helper's `connect` line below. If the row has no `id` because it is outside your reach, don't build a link; ask them to approve it in Settings › Connected apps, the [app name] row.
- **Everything else goes to a helper on a cloud model**, even when it is every app they named: one `delegate_task` per app, never a persistent agent and never added to the roster, using that app's existing `Connect [app]` child task and passing its id as `plan_node_id` (load pack `delegation` if you need it; `model` the one you run on, `bound_model` `model`; brief per "A helper's brief" below). If `delegate_task` refuses the model, post `It's on my list.` for that app and keep the task as your own. Post `Another agent looks into the rest in the background while we keep going. I'll tell you here what it finds. Next: [the next task].` An app that needs a web search to connect starts its helper only once web search has been set up; if that step ends in "not now", post `It's on my list.` for it and keep its child task as your own. Run up to three at once.
- **On the local model** (`bound_model` `source` is `omlx`) start no helper: keep each app's `Connect [app]` child task as your own, post `I'll look into [apps] after setup. Next: [the next task].`, and work those tasks after the hand-off.
- **A helper's brief** is self-contained: the app's name, whether web search works yet (`web_search_ready`, or the key just saved), and that it connects nothing itself (it has no `corsia_api`). It finds the maker's own way to connect (checked on the maker's own site) and returns exactly one of: `connect` with the name, the command and arguments or the URL, the keys it needs by name only, and the publisher it confirmed; `needs_person` with the one thing only they can do; or `nothing_connects`. It never asks the person anything and never holds a key or password.
- **When a helper returns,** post one line as soon as it lands, between steps and never as a second open question. A helper that ends with an error or nothing also wakes you through its task: post `It's on my list.` for that app and keep the task as your own. `connect`: add the app with `corsia_api` `POST /api/mcp/servers` as skill `coordination-api` says, then `[App] is ready. [Approve it](#connected-apps/<id>) in Settings › Connected apps.` with `<id>` the URL-encoded `id` returned by that call, plus the one sign-in or key it needs, if any, and settle the task with that as evidence. `needs_person`: the one thing it needs, with whose it is: yours (`It's on my list.`) or theirs with the steps in a task (`That one's yours; the steps are in your tasks.`). If it needs the person, ask right after they answer the question in front of you, so two questions are never open at once. `nothing_connects`: `Nothing connects to [app]. I'll build a connection after setup.` and keep that app's child task to build it, as skill `connect-tools` says under "No connection exists yet". Never end on "I can't".
- On "not now" or "nothing": `I'll suggest them as they come up.` Never ask again during setup.
