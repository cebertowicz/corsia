# Agent team decomposition

Build the smallest team that lowers user attention. Persistent agents own outcomes over time; they are not task containers or process stages.

## When a persistent owner is justified

Create one for a recurring, cohesive outcome whose decisions and memory improve with use enough to save more attention than the coordination costs. A finite deliverable stays a thread. Check:

- decisions and context are cohesive, so most work needs no handoff to another owner;
- the trigger recurs, or the work needs a check independent of the doer;
- memory compounds across future work;
- continuity saves more than coordination adds.

Start with the conductor and the fewest owners. Split for sustained context load, a need for independent verification, or measured failure at a boundary; merge or retire overlaps, finished responsibilities, and owners whose coordination exceeds continuity value. Name roles for stable outcomes, never a phase, model, task, or persona.

Cut vertically: one owner carries a domain end to end, from deciding what to do through delivery and checking. Two horizontal roles are legitimate because separation is the point: independent verification (the checker is not the doer) and coordination or release (one owner sequences approved work).

## One accountable owner per deliverable

Core context says who the owner is by default. Contributors keep authority over their own domains and constraints. For consequential cross-owner work, state in one line who drives, who approves, and who contributes. An unowned aggregate outcome is a gap for the conductor to assign; owning it grants accountability within the commission, not authority to start new work.

## New agents and projects

1. **Reuse first.** Look for an agent that already owns the outcome (check near-synonyms in the roster). Use it.
2. **One outcome is one agent, however big.** A project is only for work whose context nothing else should see, or that has its own way of working across several agents.
3. **The person approves a new lasting agent's charter**: what it is for and what it may do. Any other agent sends the request to the conductor (to CORSIA outside a project) and never creates one. A temporary worker for one task needs no approval.
4. **Check the setup worked.** Whoever sets up a new agent confirms that on its first real request it correctly decides one thing it is allowed to do, and hands one thing it is not allowed to do to whoever owns it.

## Delegate only separable work

Keep work inline when it is tightly coupled to your reasoning, needs continuous user alignment, no suitable worker is available, or a brief and independent verification would cost more than doing it. Otherwise delegate a self-contained step whose result can be checked without redoing it; System context's delegation rule sets when.

- Coupled mutable work has one writer. Keep or substantively review the plan; do not delegate planning and execution and forward the answer.
- Fan out only over independent pieces (no shared files, state, or owner), no wider than you can inspect and integrate. Related or exploratory problems get one worker.
- Brief: objective, acceptance evidence, groundwork and exact evidence (errors, paths, names), boundaries, what already exists, constraints blocking the lazy fix, and the return shape. Completion is evidence, not a transcript or confidence.
- On return, check for overlapping edits, run the smallest decisive check, and spot-check each worker, because workers make systematic errors that look consistent.

## What a child receives

A child inherits System, workspace, and selected-project context and the base skills it is eligible for, not your history, plan, continuity, checkpoints, or persistent-role context. Anything else it needs goes in the brief.

## Before and after spawning

- Choose only a model the catalog or status tool reports as ready, fitted to the work under the workspace's spawn policy; never rebind onto a non-ready one. Use only capacity, budget, and utilization signals the tools return; when none is exposed, say so instead of assuming.
- Treat a dispatch as undelivered until the child produces a real turn. For a quiet or empty child, read its status and last error first, then re-brief or rebind to an available model.

## Improvement boundary

Each agent maintains its own responsibility-local sources and lessons inside its mission. Structural change (mission, boundaries, authority, grants, core skills) is proposed to the conductor and user, never self-applied. A recurring improvement loop needs durable history, a narrow external success measure, and an independent check; never create one that grades itself.
