# Cross-agent read (project conductor)

With no daily intake, run on your first turn seven or more days after the ledger's last read date.

Schedule nothing new; run this inside the wake or turn your conductor role context names. Keep `working/cross-agent-read.md` in your thread folder (create it silently): one line per lesson id and version you have read, and one line per pattern you routed.

1. **Read your project only.** Call `lesson_report(scope="project", project=<your project id>, state="watch")`, then again with `state="trial"`, following `next_cursor` until it is null. Never pass another project id or `scope="all"`. Skip every id and version already in your ledger. Until agents record watch items routinely, expect this read to return few or none; an empty read means nothing new was recorded, not that no pattern exists. Read any other lesson source your coordination model names the same way.
2. **Restate each new item** in one line: the decision that went wrong, with no names, dates, ids or task details. Write its cause beside it, using the seven causes in `memory-placement` §4 (wrong rule, no foundation, rule gap, process gap, not delivered, not followed, can't be done); use the item's own recorded cause when it has one. Before writing *rule gap*, search the guidance the owner was delivered (System context and skills, project context, its own bootloader and skills; read them through the effective-context view if you have one, else the source files by layer, and say which you used) for a rule that already covers the decision; if one does, the cause is *not delivered* when that rule never reached the owner's turn (wrong layer, or a skill that didn't trigger), *not followed* when it did, and *wrong rule* when following it produced the bad decision; never *rule gap*.
3. **Group.** Two items are the same pattern when the same decision went wrong for the same cause. Matching words, the same topic, or the same person's name do not make a pattern. A group needs at least two different owners (`owner_ids`). One owner repeating itself is its own lesson's business; leave it. Test each pair by asking whether one fix would help both; if a fix for one would make the other worse, they are different patterns.
4. **Route each group** by `SKILL.md`'s Prove it and Promote. Write the scenario set from the items (the failing task shape, an ordinary success, a boundary case that must not trigger). Then apply the remedy `memory-placement` §4 gives for that cause, at the shared layer: place a project-layer rule yourself; for a System one, follow Promote's upstream route; for *not followed*, write no new text and recommend a control, as an option, to whoever owns the gate or tool. Never edit another agent's guidance or lesson file. Tell each affected owner once, through the route your coordination model gives the conductor for cross-agent patterns (a plan task on the owner's plan where allowed, never a direct message per agent), carrying the group line and the lesson ids. When most of the project's agents share the pattern, use one project-wide notice instead.
5. **Record** the read date, ids you read, and each group you routed in the ledger.
6. **If nothing matches, do nothing else.** Record the read date and ids as read. Send no message, add no plan node, raise nothing to the person.
